# nkit-claude-code 프레임워크 분석 — 실전 AI 에이전트 하네스 사례 연구

이 문서는 **nkit-claude-code**(PowerBuilder → Java/Nexacro 마이그레이션 & 신규 프로그램 개발 AI 프레임워크, v3.11.0)를 교육 관점에서 분석합니다. 우리 교육 하네스(`ai-edu/harness`)의 PDCA 엔진이 이 프레임워크에서 유래했으므로(→ `2.PDCA-방법론.md`), "교육용 하네스가 실무 규모로 확장되면 어떤 모습이 되는가"를 보여주는 실전 사례로 읽으면 좋습니다.

- 분석 대상: `nkit-claude-code` (Claude Code 플러그인 형태의 AI 프레임워크)
- 함께 보기: `2.PDCA-방법론.md`(방법론), `4.사이트별-컨벤션.md`(규칙 적용 체계)

## 1. nkit-claude-code란 무엇인가요?

레거시 **PowerBuilder** 화면을 **Java(EgovFramework/Spring MVC) + Nexacro** 스택으로 자동 마이그레이션하거나, **PPTX 설계서**를 기반으로 신규 프로그램을 개발하는 Claude Code 기반 프레임워크입니다.

| 항목 | 내용 |
|------|------|
| 형태 | Claude Code **플러그인** (marketplace 설치) |
| 방법론 | **PDCA 7단계** (Plan → Extract → Design → Do → Check → Iterate → Report) |
| 규모 | 에이전트 46개 · 스킬 51개 · 슬래시 명령어 55개 · Hook 31개 · 규칙 29개 |
| 대상 스택 | Java 1.8 + Spring MVC 4.3 + EgovFramework 3.8 + MyBatis + Nexacro N 17 + Oracle 11g |
| 핵심 특징 | 행동 강제 게이트(Iron Law/HARD-GATE), Continuous Learning v2(자가 학습), 2단계 병렬 실행 |

### 왜 이 사례를 배우나요?

우리 교육 하네스가 "에이전트 27종 + 커맨드 40종 + PDCA 6단계"의 **학습용 축소판**이라면, nkit은 같은 설계 사상을 **실무 마이그레이션 프로젝트 규모**로 키운 것입니다. 다음 질문에 대한 실전 답을 보여줍니다.

1. AI 에이전트에게 어떻게 **일관된 품질**의 코드를 만들게 하는가? → 품질 게이트 + Hook 강제
2. AI가 자주 틀리는 패턴을 어떻게 **시스템적으로 차단**하는가? → 절대 금지 규칙 + 인스팅트
3. 팀이 발견한 노하우를 어떻게 **재사용 가능한 자산**으로 만드는가? → Continuous Learning v2
4. 수백 개 화면을 어떻게 **병렬로** 처리하는가? → 다중 화면/단계 내 병렬 실행

## 3. 사용 워크플로우 (팀원 관점)

팀원 한 사람의 사용 흐름은 5단계입니다.

```
┌──────────────────────────────────────────────────────┐
│ 최초 1회:  ① repo 2개 clone  → ② ./install-plugin.sh │
├──────────────────────────────────────────────────────┤
│ 매 세션:   ③ /pdca-full <화면ID>  (작업)             │
│            ④ /learn, /evolve      (학습 축적)        │
│            ⑤ git push             (생성 코드 공유)   │
└──────────────────────────────────────────────────────┘
```

- **①②** `nkit-claude-code`(프레임워크)와 `ndserp`(타겟 소스)를 같은 폴더에 나란히 clone하고, 설치 스크립트가 플러그인 등록·환경 변수·MCP 서버·학습 저장소까지 11단계로 자동 구성합니다.
- **③** 마이그레이션은 `/pdca-full`, 신규 개발은 `/pdca-new`로 실행합니다(4장).
- **④** 세션에서 발견한 패턴을 인스팅트로 저장하고, 성숙하면 스킬로 승격합니다(7장).
- **⑤** 생성된 Java/XFDL 코드는 타겟 repo(`ndserp`)로 push해 팀과 공유합니다.

설치가 **스크립트 한 번**으로 끝나도록 만든 점이 교육적으로 중요합니다. 도구가 아무리 강력해도 셋업이 어려우면 팀에 정착하지 않습니다.

## 4. PDCA 7단계 파이프라인

우리 하네스의 6단계(plan→design→do→check→iterate→report)와 달리, nkit은 **Extract**(레거시 소스 분석) 단계가 추가된 7단계입니다.

| 단계 | 담당 에이전트 | 산출물 |
|------|--------------|--------|
| 1. Plan | migration-pm | 계획 문서 (복잡도, 일정) |
| 2. **Extract** | pb-analyzer | PB 소스 구조 분석 JSON |
| 3. Design | java-architect ∥ nexacro-architect | 설계 문서 |
| 4. Do | java-architect ∥ nexacro-architect | Java/XML/XFDL 코드 |
| 5. Check | code-reviewer, gap-detector | 품질 검증 리포트 (L1~L3) |
| 6. Iterate | migration-iterator | 미달 항목 자동 수정 → Check 재진입 |
| 7. Report | migration-reporter | 완료 보고서 |

### 4-1. 두 가지 입력 소스: 마이그레이션 vs 신규 개발

같은 파이프라인이 입력 소스만 바꿔 재사용됩니다. **앞 2단계(Plan/Extract)만 다르고 Design 이후는 동일**합니다 — 파이프라인 재사용 설계의 좋은 예입니다.

| 구분 | 마이그레이션 `/pdca-full` | 신규 개발 `/pdca-new` |
|------|---------------------------|------------------------|
| 입력 | PB `.srw/.srd` 소스 | **PPTX 설계서** |
| Extract 도구 | `parse_pb.py` (Python 파서) | python-pptx + **Claude Vision** |
| 검증 기준 (L3) | PB ↔ Java 로직 동등성 | PPTX 명세 ↔ 구현 일치도 |

신규 개발의 PPTX 파싱은 **하이브리드**입니다: 텍스트/테이블은 python-pptx로 기계 추출하고, UI 목업 슬라이드만 Claude Vision으로 분석해 비용과 정확도의 균형을 잡습니다. 또 Design 전에 HTML 프로토타입을 만들어 브라우저에서 시각 검증하는 옵션 단계(Phase 2.5)도 있습니다 (`/proto-screen` → 확인 → `/proto-to-xfdl`).

### 4-2. 2단계 병렬 실행

```
(1) 다중 화면 병렬:  /pdca-parallel AA21101,AA21102,AA21103
     ┌─ AA21101: Plan→Extract→Design→Do→Check→Report ─┐
     ├─ AA21102: Plan→Extract→Design→Do→Check→Report ─┤  동시 실행
     └─ AA21103: Plan→Extract→Design→Do→Check→Report ─┘

(2) 단계 내 병렬 (기본 활성):
     Design:  java-architect  ∥  nexacro-architect
     Do:      Java 코드 생성  ∥  Nexacro 코드 생성
     Check:   L1(코드품질) ∥ L2(설계일치)  →  L3(로직일치)
```

백엔드(Java)와 프론트엔드(Nexacro)는 서로 독립이므로 동시에 진행하고, 의존성이 있는 단계(Plan, Extract, Report)는 순차 실행합니다. **"독립적인 작업만 병렬화한다"**는 원칙이 일관되게 적용되어 있습니다.

## 5. 품질 게이트 — AI 출력을 신뢰 가능하게 만드는 장치

Check 단계는 **순차 3단계(+런타임) 게이트**입니다. 앞 게이트를 통과해야 다음을 평가합니다.

| 게이트 | 검증 내용 | 기준 |
|--------|----------|------|
| **L1** | 코드 품질 (린트, 복잡도, 컨벤션) | ≥ 90점 |
| **L2** | 설계 일치 (구현이 Design 문서와 일치하는가) | ≥ 90% |
| **L3** | **로직/명세 일치** (PB 원본 또는 PPTX 명세와 동등한가) | ≥ 90% — **CRITICAL** |
| L4 | 빌드/런타임 | ≥ 90% |

미달 시 Iterate 단계가 자동으로 수정 후 재검증하며, 최대 반복 횟수 안에 통과하지 못하면 **잔여 이슈를 보고서에 명시하고 미완료로 남깁니다**. "묵시적 통과 처리 금지"는 우리 하네스에도 그대로 계승된 원칙입니다.

## 6. Hook 시스템 — 행동을 "권고"가 아니라 "강제"하는 법

AI에게 "하지 마세요"라고 프롬프트에 적는 것과, **시스템이 그 행동을 차단**하는 것은 신뢰성이 다릅니다. nkit은 Claude Code의 8종 Hook 이벤트(PreToolUse, PostToolUse, PostToolUseFailure, SessionStart, Stop, Notification, PreCompact, SessionEnd)에 31개 스크립트를 등록해 후자를 구현합니다.

대표 사례를 목적별로 보면:

| 목적 | Hook (이벤트) | 동작 |
|------|---------------|------|
| **위험 차단** | block-no-verify.js (PreToolUse) | `git commit --no-verify` 플래그 차단 |
| **위험 차단** | config-protection.js (PreToolUse) | AI가 린터/빌드 설정을 멋대로 고치는 것 차단 |
| **품질 강제** | quality-gate.js (PostToolUse) | 파일 쓸 때마다 Java/Nexacro/MyBatis 품질 자동 검증 |
| **품질 강제** | check-console-log.js (Stop) | 세션 종료 시 디버그 출력문(console.log 등) 탐지 |
| **사실 강제** | gateguard-fact-force.js (PreToolUse) | 파일 수정 전 "실제 코드를 조사했는가"를 강제 |
| **보안** | commit-quality.js (PreToolUse) | 커밋 전 시크릿(비밀번호/키) 감지 |
| **학습 수집** | observe.sh (Pre/PostToolUse) | 모든 도구 사용을 관측 데이터로 기록 (7장) |
| **운영 편의** | desktop-notify.js (Stop) | 작업 완료 데스크톱 알림 |
| **비용 관리** | cost-tracker.js (Stop) | 토큰 비용 추적 |

교육 포인트: Hook은 **결정적(deterministic)** 입니다. AI의 판단에 의존하지 않고 항상 실행되므로, "절대 일어나면 안 되는 일"은 프롬프트가 아니라 Hook에 넣어야 합니다.

### 절대 금지 규칙 (도메인 지식의 코드화)

CLAUDE.md에 명문화된 금지 규칙은 이 프로젝트에서 AI가 **실제로 자주 틀렸던 패턴**의 목록입니다. 몇 가지 예:

| 금지 | 이유 / 대안 |
|------|-------------|
| `@RestController` 사용 | EgovFramework는 `@Controller extends AbstractController` 필수 |
| `StringUtil.nvl()` 호출 | 이 프로젝트에 **존재하지 않는 메서드** (AI가 환각으로 자주 생성) → `Objects.toString()` |
| SQL `${}` 바인딩 | SQL 인젝션 위험 → `#{}` 필수 |
| 스키마 접두사 누락 | `NDSERP.TB_*` 필수 (Oracle 다중 스키마 환경) |
| PB 파일 직접 Read | CP949/UTF-16LE 인코딩이 깨짐 → 전용 파서(`parse_pb.py`) 사용 |
| PDCA 단계 생략 | 품질 게이트 우회 방지 |

여러분의 사이트에서도 "AI가 반복해서 틀리는 것"을 발견하면 이런 식으로 **금지 규칙 + 대안**의 쌍으로 명문화하는 것이 컨벤션 팩(→ `4.사이트별-컨벤션.md`)의 핵심입니다.

## 7. Continuous Learning v2 — 스스로 성장하는 하네스

nkit에서 가장 독창적인 부분입니다. 세션에서 발견한 패턴을 **인스팅트(Instinct)**라는 단위로 저장하고, 신뢰도(confidence)를 관리하며, 성숙한 인스팅트를 스킬로 **진화**시킵니다.

```
observe.sh (Hook, 자동)  →  observations.jsonl (관측 데이터)
                                  ↓  Observer Agent 분석
/learn (수동 저장)        →  인스팅트 저장소 (~/.claude/homunculus/)
                                  ↓  주간 confidence 감쇠
/evolve (클러스터링)      →  유사 인스팅트 묶음 → 스킬/에이전트 자동 생성
                                  ↓
/instinct-promote         →  정식 스킬로 승격
```

### 인스팅트 confidence 체계

| 점수 | 의미 | 동작 |
|------|------|------|
| 0.9 이상 | 거의 확실 | 승격 후보, 핵심 동작 |
| 0.7~0.89 | 강함 | 자동 적용 |
| 0.5~0.69 | 보통 | 관련 시 적용 |
| 0.3~0.49 | 잠정적 | 제안만 |
| 0.2 미만 | 소멸 | 자동 삭제 |

변동 규칙: 확인 관측 +0.05, 모순 관측 −0.10, 주간 무관측 −0.02 (감쇠).

생물의 학습과 비슷합니다 — 반복 확인된 패턴은 강해지고, 모순되면 빠르게 약해지고, 쓰이지 않으면 서서히 잊힙니다. 단, 핵심 규칙 13개는 **큐레이션 인스팅트**로 지정되어 감쇠 대상에서 제외됩니다(예: "EgovFramework 패턴 강제" 0.98, "StringUtil.nvl() 미존재" 0.97).

### 팀 학습 공유

`/instinct-export` / `/instinct-import`로 팀원 간 인스팅트를 JSON으로 주고받고, `/skill-create`는 Git 커밋 히스토리에서 패턴을 추출해 스킬 문서를 생성합니다. **개인의 시행착오가 팀의 자산이 되는 구조**입니다.

## 8. 도구 통합 — MCP 서버와 Python 도구

LLM이 직접 못 하는(또는 비효율적인) 일은 전용 도구에 위임합니다.

| 도구 | 종류 | 역할 |
|------|------|------|
| `parse_pb.py` | Python CLI | PB 소스 → 구조화 JSON (PDCA 파이프라인 주력 파서) |
| pb-parser-mcp | MCP 서버 | 단건 PB 파싱 (대화 중 빠른 확인용, 보조) |
| `extract_pptx.py` | Python CLI | PPTX 텍스트/테이블/이미지 추출 + 슬라이드 분류 |
| pdf-reader-mcp | MCP 서버 | PDF(UbiReport) 분석 |
| github / memory / playwright | MCP 서버 | PR 리뷰, 세션 간 메모리, E2E 브라우저 테스트 |

같은 PB 파싱에 도구가 둘인 이유: **"파이프라인 안이면 CLI(기능 풍부), 대화 중 단발 확인이면 MCP(기동 비용 0)"**라는 명확한 선택 기준을 두고 병행합니다. 흥미로운 운영 사례로, 실사용처가 0건인 MCP 서버 2개(context7, sequential-thinking)를 측정 후 **제거**한 이력도 있습니다 — 도구는 많을수록 좋은 게 아니라, 쓰이는 것만 남기는 것이 컨텍스트 비용 관리입니다.

## 10. 핵심 교훈 정리

실무 AI 프레임워크를 설계할 때 nkit에서 가져갈 수 있는 원칙 6가지입니다.

1. **방법론을 명령어로 굳히세요.** "PDCA로 하자"는 합의는 흩어지지만, `/pdca-full` 한 줄이면 모두가 같은 절차를 밟습니다.
2. **금지는 프롬프트가 아니라 Hook으로.** 반드시 막아야 할 행동은 결정적 코드(PreToolUse 차단)로 강제해야 합니다.
3. **품질은 측정 가능한 게이트로.** "좋은 코드"가 아니라 "L1 ≥ 90, L2 ≥ 90%, L3 ≥ 90%"처럼 수치 기준과 자동 재시도(Iterate)를 두세요. 미달이면 미완료로 보고하고, 묵시적 통과는 금지합니다.
4. **AI의 실수를 자산으로.** 반복되는 환각/오류 패턴(예: 존재하지 않는 메서드 호출)을 금지 규칙·인스팅트로 축적하면 프레임워크가 점점 똑똑해집니다.
5. **LLM이 못 하는 일은 도구로.** 인코딩이 특수한 파일 파싱, PPTX 추출 같은 기계적 작업은 Python/MCP 도구에 위임하고, AI는 판단에 집중시키세요.
6. **독립 작업만 병렬화.** Java ∥ Nexacro처럼 의존성이 없는 축은 병렬로, 의존성이 있는 단계는 순차로 — 구조가 속도를 만듭니다.
