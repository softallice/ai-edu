# PDCA 방법론 — OpenCode 하네스 적용 가이드

이 문서는 `nkit-claude-code`(PowerBuilder → Java/Nexacro 마이그레이션 프레임워크)의 **PDCA 엔진**을 분석해, 마이그레이션 특화 요소를 제거한 **제네릭 PDCA 방법론**을 우리 OpenCode 하네스(`harness/`)에 적용한 결과를 설명합니다.

대상 환경: WSL + 로컬 Ollama(`qwen2.5-coder:7b`) + OpenCode + Java/Spring Boot · React (`1.환경설정.md` 참고)

---

## 1. PDCA란 무엇인가

PDCA는 **Plan(계획) → Do(실행) → Check(점검) → Act(개선)** 를 반복하는 품질 관리 사이클입니다. AI 에이전트 개발에 적용하면, "한 번에 코드를 쏟아내고 끝"이 아니라 **계획을 세우고 → 구현하고 → 품질을 측정하고 → 기준 미달이면 자동으로 고쳐 다시 검증**하는 통제된 흐름이 됩니다.

본 하네스는 nkit의 7단계를 6단계로 일반화했습니다.

| 단계 | PDCA 매핑 | 목적 |
|------|----------|------|
| **plan** | Plan | 요구사항·범위·리스크 정의, 작업 분해 |
| **design** | Plan | 아키텍처/API/데이터/UI 설계 문서화 |
| **do** | Do | 설계대로 코드 구현 |
| **check** | Check | 품질 게이트(L1~L4) 검증 |
| **iterate** | Act | 게이트 미달 항목 자동 수정 후 재검증(반복) |
| **report** | Act | 완료 보고서 작성 + 상태 갱신 |

> 별칭: `analyze`→plan, `implement`→do, `verify`→check, `act`→iterate

---

## 2. 전체 흐름

```
plan → design → do → check ──(게이트 전부 통과)──────────→ report
                         └─(미달)→ iterate → check ↺ (최대 3회) ─┘
```

- 각 단계는 앞 단계의 산출물을 전제로 합니다(문서 의존성). 단계 생략은 금지됩니다.
- `check`에서 품질 게이트가 하나라도 미달하면 `iterate`로 분기해 수정 후 다시 `check`합니다.
- `maxIterations`(기본 3) 안에 통과하지 못하면, `report`에 잔여 이슈를 명시하고 미완료로 남깁니다. **묵시적 통과 처리는 금지**됩니다.

---

## 3. 품질 게이트 (Check 단계)

순차 검증입니다. 앞 게이트를 통과해야 다음 게이트를 평가합니다.

| 게이트 | 담당 에이전트 | 기준 | 비고 |
|--------|--------------|------|------|
| **L1 코드 품질** | code-reviewer + security-reviewer | ≥ 80점 | 린트/복잡도/가독성/보안 |
| **L2 설계 일치** | code-reviewer | ≥ 90% | 구현이 plan/design과 일치 |
| **L3 테스트·동작 일치** | tdd-guide | ≥ 90% | **CRITICAL — 반드시 통과** |
| **L4 빌드·런타임** | build / e2e-runner | ≥ 90% | 빌드/실행/E2E 스모크 |

기준값은 `harness/config/pdca.config.json`의 `qualityGates`에서 조정합니다.

---

## 4. 단계별 담당 에이전트 (Handoff)

각 단계는 전문 에이전트에 위임되고, 결과는 `docs/pdca/`에 마크다운으로 남겨 다음 단계가 읽습니다.

| 단계 | 에이전트 | 산출물 경로 |
|------|---------|-------------|
| plan | `planner` | `docs/pdca/01-plan/{feature}.plan.md` |
| design | `architect` | `docs/pdca/02-design/{feature}.design.md` |
| do | `build` | 실제 소스 코드 |
| check | `code-reviewer` · `security-reviewer` · `tdd-guide` | `docs/pdca/03-check/{feature}-{quality,gap,test}.md` |
| iterate | `build-error-resolver` · `refactor-cleaner` · `tdd-guide` | (수정 후 재검증) |
| report | `doc-updater` | `docs/pdca/04-report/{feature}.report.md` |

전체 흐름은 `pdca-orchestrator`(primary 에이전트)가 조율합니다.

## 5. 사용법 (커맨드)

```bash
# 전체 PDCA 루프 자동 실행
/pdca-full login-api
/pdca-full login-api --auto          # 단계 간 확인 없이 진행
/pdca-full login-api --skip-iterate  # 게이트 미달이어도 iterate 생략
/pdca-full login-api --from check    # 중단 지점부터 재개

# 단일 단계 실행
/pdca plan login-api
/pdca design login-api
/pdca do login-api
/pdca check login-api
/pdca iterate login-api
/pdca report login-api

# 진행 상태 / 다음 단계
/pdca-status
/pdca-next
```

자연어로도 트리거됩니다: "login-api 기능 계획 세워줘", "품질 검증해줘", "전체 PDCA 한 번에 돌려줘" 등.

## 6. 상태 추적 (`.pdca-status.json`)

`pdca-status` 도구가 단계 종료마다 진행 상태를 파일에 영속화합니다.

```json
{
  "version": "1.0.0",
  "updatedAt": "2026-06-09T...",
  "features": {
    "login-api": {
      "currentPhase": "check",
      "completed": false,
      "iterationCount": 1,
      "gates": { "L1_codeQuality": 92, "L2_designMatch": 95, "L3_testMatch": 88, "L4_runtime": 90 },
      "generatedFiles": ["src/main/java/.../LoginController.java"],
      "notes": "L3 미달 — 토큰 만료 케이스 테스트 누락"
    }
  }
}
```

- `/pdca-status` → 도구 `action=show`로 표 출력
- 각 단계 → 도구 `action=update`로 갱신

또한 컨텍스트 압축 훅(`experimental.session.compacting`)이 이 파일을 읽어 **PDCA 진행 상태를 압축 후에도 보존**합니다. 로컬 7B 모델의 제한된 컨텍스트에서 장시간 작업의 연속성을 지키는 핵심 장치입니다.

## 7. 작업 복잡도 등급

`config/pdca.config.json`의 `taskClassification` 기준으로 작업 무게를 조절합니다.

| 등급 | 작업 단위 | PDCA 레벨 |
|------|----------|-----------|
| simple | < 5 | light (design을 plan에 흡수, iterate 생략 가능) |
| standard | 5–15 | standard |
| complex | 15–30 | full |
| very complex | > 30 | sectional(분할 분석) |

> 단, 어떤 등급이든 **L3(테스트·동작) 게이트는 항상 수행**합니다.

## 8. nkit 대비 변경·제외 항목

| 구분 | nkit (원본) | 본 하네스 (이식) |
|------|------------|------------------|
| 단계 | plan→**extract**→design→do→check→iterate→report (7) | plan→design→do→check→iterate→report (6) |
| extract | PB 소스 `parse_pb.py` 파싱 | **제외** (마이그레이션 특화) |
| do | Java/Nexacro/MyBatis 6파일 생성 | 범용 코드 구현 |
| 품질 L3 | PB-Java 로직 동치(Logic Match) | 테스트·동작 일치 |
| 모델 라우팅 | opus/sonnet/haiku 단계별 | **로컬 단일 모델로 통일** |
| 상태 파일 | `.migration-status.json` | `.pdca-status.json` |
| 병렬 | `/pdca-parallel` 다중 화면 | **제외** (로컬 7B 단일 모델에서 단일 흐름이 명확) |

## 10. 실전 예시

```bash
cd harness
opencode

# 새 기능을 PDCA로 개발
/pdca-full user-search

# → plan: 요구사항/리스크/작업 분해 (planner)
# → design: API·데이터·UI 설계 (architect)
# → do: 구현 (build)
# → check: L1 92 / L2 95 / L3 85 / L4 90  → L3 미달!
# → iterate: 누락 테스트 보강 (tdd-guide) → check 재실행 → L3 93
# → report: 완료 보고서 + .pdca-status.json 갱신

/pdca-status    # 전체 진행 상태 확인
```

> 참고: 로컬 7B 모델은 컨텍스트가 제한적이므로, 단계 간 핸드오프 문서와 `strategic-compact` 스킬을 적극 활용하면 안정적입니다.
