# AI 교육 커리큘럼 — 에이전트 코딩 과정

이 문서는 ai-edu 저장소의 자산(교육 문서 8종 · 하네스 2종 · 실습 템플릿 2종)을 기반으로 한
**AI 보조 개발(에이전트 코딩) 교육 과정**의 커리큘럼입니다. 강사·교육 운영자용 운영 가이드를 포함합니다.

---

## 1. 과정 개요

| 항목 | 내용 |
|------|------|
| **대상** | AI 보조 개발을 처음 배우는 사내 개발자 (Java/웹 개발 경험 전제) |
| **목표** | ① AI 에이전트로 계획→구현→검증하는 흐름 체득 ② PDCA 품질 게이트로 통제된 개발 ③ 사이트 컨벤션 적용 ④ 실무 환경(Claude Code) 전환 능력 |
| **기간** | 8차시 (차시당 2~3시간) — 2일 집중 / 주 1회 8주 중 선택 (6장 운영 옵션) |
| **전제 조건** | Windows PC(WSL 가능), Git 기본, REST API·웹 프론트엔드 개념 |
| **실습 환경** | 1~5차시: 로컬 무료(OpenCode+Ollama) · 6차시~: 실무(Claude Code, API 키 필요) |

### 과정 설계 원리

1. **로컬 → 실무의 2단계 트랙**: 비용 없는 로컬 모델로 개념·습관을 익히고, 같은 워크플로우를 클라우드 Claude로 전환합니다. 두 하네스(`harness/`, `harness-claude-code/`)가 동일한 PDCA·커맨드·컨벤션 체계를 제공하므로 전환 비용이 낮습니다.
2. **실습 중심**: 매 차시 실제 템플릿(`backend/` Task API, `frontend/` 관리자 화면)에 기능을 추가하며 배웁니다.
3. **기존 문서가 교재**: 차시마다 `docs/1~8`을 교재로 지정합니다 — 별도 교안 제작 불필요.
4. **품질을 처음부터**: "AI가 짠 코드를 어떻게 믿는가"를 과정 전체의 관통 질문으로 두고, 게이트·훅·리뷰를 매 차시 반복합니다.

## 3. 차시별 상세

### 1차시 — AI 에이전트 코딩 개요 + 환경 구축

- **목표**: 에이전트 코딩이 무엇인지(자동완성 vs 에이전트), 왜 하네스가 필요한지 이해하고 로컬 환경을 완성합니다.
- **이론(40분)**: LLM 코딩 도구의 스펙트럼(자동완성→챗→에이전트) · 에이전트의 구성(도구 호출, 계획, 반복) · 로컬 모델 vs 클라우드 모델 트레이드오프(docs/7의 하드웨어 표)
- **실습(80분)**: docs/1의 1~5단계 — WSL·Node·Ollama(`qwen2.5-coder:7b` 또는 저사양 `3b`)·OpenCode 설치 → `ai-edu` clone → 설치 검증 4종(`node -v`, `ollama list`, `opencode --version`, `curl localhost:11434/api/tags`)
- **산출물**: 설치 검증 스크린샷
- **막히는 지점**: NPU 노트북은 Ollama가 못 씀 → 3b 모델 권장 (docs/5 3-1)

### 2차시 — 에이전트 첫 경험: 하네스 구조 이해

- **목표**: 하네스의 5요소(에이전트·커맨드·스킬·훅·컨벤션)를 구분하고, 자연어와 커맨드로 코드를 생성·리뷰합니다.
- **이론(40분)**: 하네스란 무엇인가(docs/5 1장) · 에이전트 27종/커맨드 40종의 역할 분류 · "왜 그냥 챗으로 안 하나" — 일관성·품질·재현성
- **실습(80분)**: `harness/`에서 `opencode` 실행 → 자연어 요청("간단한 todo 함수") → `/plan`으로 계획-승인 흐름 체험 → `/code-review`로 생성 코드 리뷰 → 의도적으로 나쁜 코드를 요청해 리뷰가 잡아내는지 관찰
- **산출물**: 계획서 1건 + 리뷰 결과 1건
- **핵심 메시지**: "한 번에 시키지 말고, 계획→승인→구현→리뷰로 쪼갠다"

### 3차시 — PDCA 방법론: 백엔드 기능 개발

- **목표**: 품질 게이트(L1~L4) 기반의 통제된 개발 루프를 체득합니다.
- **이론(40분)**: docs/2 — 6단계(plan→design→do→check→iterate→report), 게이트 기준(L1 코드품질 ≥80 · L2 설계일치 ≥90% · L3 테스트 ≥90% CRITICAL · L4 빌드), "묵시적 통과 금지" 원칙
- **실습(80분)**: `backend/`(Spring Boot Task API)에서 `/pdca-full task-comment` — Task에 댓글 기능 추가. 단계별 산출물(`docs/pdca/`)을 열어 보며 진행 → 게이트 미달 시 iterate가 자동 수정하는 과정 관찰 → `/pdca-status`로 상태 확인
- **산출물**: PDCA 보고서(`docs/pdca/04-report/`) + 게이트 점수
- **막히는 지점**: 로컬 7B의 한계로 큰 기능은 실패 → 작게 쪼개는 연습 자체가 교육 목표

### 4차시 — 프론트엔드 실습: 템플릿 구조와 화면 개발

- **목표**: 실제 규모의 프론트 코드베이스(shadcn-admin 기반)에서 에이전트로 기능을 추가합니다.
- **이론(30분)**: docs/6 — features/ 구조, TanStack Router/Query/Table, 하네스·컨벤션과의 연동
- **실습(90분)**: `frontend/`에서 PDCA로 "Task 통계 카드" 또는 "목록 필터" 추가 → `pnpm dev`로 브라우저 확인 → `/verify`(빌드·린트·테스트 일괄)
- **산출물**: 동작하는 화면 + verify 통과 로그
- **핵심 메시지**: "에이전트는 기존 코드 패턴을 따라간다 — 템플릿 구조가 좋을수록 결과가 좋다"

### 5차시 — 사이트별 컨벤션: 규칙의 코드화

- **목표**: 사이트(프로젝트)마다 다른 코딩 규칙을 컨벤션 팩으로 적용하고, AI 출력이 규칙을 따르게 만듭니다.
- **이론(40분)**: docs/4 — 베이스+overlay 구조, 팩 5종(common·react-typescript·spring-boot·nexacro·egov-backend), 프로파일. "AI가 반복해서 틀리는 것"을 금지 규칙+대안 쌍으로 명문화하는 법(docs/8 6장의 nkit 사례 연결)
- **실습(80분)**: 실습 폴더에 `apply-convention.cjs`로 spring-boot 팩 적용 → 같은 요청을 컨벤션 적용 전/후로 비교 → 자기 팀 규칙 1개를 골라 컨벤션 팩 형식으로 작성해 적용
- **산출물**: 자작 컨벤션 규칙 1건 + 적용 전후 비교 메모

### 6차시 — 실무 전환: Claude Code 하네스와 훅

- **목표**: 같은 워크플로우를 실무 환경(클라우드 Claude, 멀티 티어)으로 전환하고, 훅이 "권고"가 아니라 "강제"임을 체험합니다.
- **이론(40분)**: harness-claude-code/README — 로컬 vs 클라우드 비교(신뢰도·비용, docs/7 결론), 설치 3모드(교육/전역/프로젝트), 모델 티어링(opus/sonnet/haiku), 훅 8종
- **실습(80분)**:
  1. `./install.sh`(또는 교육 모드로 폴더 내 실행) → `/help`로 커맨드 확인
  2. **훅 차단 체험**: 가짜 API 키(`sk-...`)를 파일에 넣고 커밋 시도 → commit-quality 훅 차단 관찰 · `.prettierrc` 수정 요청 → config-protection 차단 관찰
  3. 3차시와 같은 기능을 `/pdca-full`로 재실행 → 로컬 7B 결과와 품질·속도 비교
- **산출물**: 차단 사례 2건 캡처 + 로컬/클라우드 비교 소감
- **핵심 메시지**: "반드시 막아야 할 것은 프롬프트가 아니라 훅(코드)으로 막는다"

### 7차시 — 학습하는 하네스: Continuous Learning v2

- **목표**: 세션에서 발견한 패턴을 인스팅트로 축적하고 팀 자산으로 공유하는 루프를 익힙니다.
- **이론(40분)**: CL-v2 구조(관측 훅 → 인스팅트 → confidence → 진화) · confidence 체계(0.3 잠정 ~ 0.9 확실) · nkit의 큐레이션 인스팅트 사례(docs/8 7장)
- **실습(80분)**: 작업 중 발견한 패턴을 `/learn "..."` 으로 저장 → `/instinct-status`로 confidence 막대 확인 → observer 에이전트로 관측 데이터 일괄 분석 → `/instinct-export`로 내보내 옆 사람과 `/instinct-import` 교환
- **산출물**: 인스팅트 3건 + 팀 교환 1회
- **핵심 메시지**: "개인의 시행착오를 팀의 자산으로"

### 8차시 — 실무 프레임워크 사례와 확장 + 최종 과제

- **목표**: 교육 하네스가 실무 규모로 확장된 사례(nkit)를 분석하고, 자기 팀 적용 계획을 설계합니다.
- **이론(60분)**: docs/8 — nkit-claude-code 사례 연구(46 에이전트·PDCA 7단계·행동 강제 게이트·CL-v2) → 핵심 교훈 6가지 토론 · docs/3 — 폐쇄망/GPU 서버 확장 옵션 개요
- **실습·토론(60분)**: 팀별로 "우리 사이트 적용 계획서" 작성 — 대상 프로젝트, 적용할 컨벤션 팩(또는 신규 팩), 필요한 훅, 도입 단계(파일럿→확산)
- **산출물**: 적용 계획서 (최종 과제의 일부)

## 4. 최종 과제와 수료 기준

**최종 과제**: 실습 템플릿(backend 또는 frontend)에 자율 선택 기능 1건을 **PDCA 전체 루프**로 개발

| 평가 항목 | 기준 | 배점 |
|----------|------|------|
| PDCA 보고서 | 전 단계 산출물 존재 + 게이트 점수 명시 (미달 항목은 원인 기록 — 묵시적 통과 감점) | 40 |
| 품질 게이트 | L3(테스트·동작) 통과 필수, L1·L2·L4 ≥기준 | 30 |
| 인스팅트 | 과정 중 저장한 인스팅트 3건 이상 (원자성·트리거 구체성) | 15 |
| 적용 계획서 | 8차시 산출물 — 실행 가능성·구체성 | 15 |

수료: 70점 이상 + L3 게이트 통과. **게이트 미달을 정직하게 기록한 보고서가 부풀린 보고서보다 높게 평가**됩니다(과정의 핵심 가치).
